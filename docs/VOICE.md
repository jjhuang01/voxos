# 语音质量：我们和豆包 / ChatGPT 差在哪，怎么补

这份文档回答三个问题：**别人是怎么做到「丝滑」的**、**我们现在差在哪（有实测数据）**、
**要买什么、怎么改**。每一条都尽量给出来源，能抄的直接写「抄自哪」。

> 一句话结论：**我们缺的不是「更好的 VAD」，是三层东西——流式识别、语义判停、回声消除。**
> 端点静音从 800ms 降到 500ms、省掉一次重复解码，这些是当天就能拿到的 **228–320ms**（已实测）；
> 再往下必须换架构，靠调参调不出来。

---

## 1. 先把「丝滑」拆成可测量的东西

用户说「丝滑」，落到工程上是六个独立指标。它们互相拉扯，不可能同时最优，
所以必须先定义清楚在优化哪个：

| 指标 | 定义 | 豆包 / ChatGPT 的量级 | 我们的现状 |
| :--- | :--- | :--- | :--- |
| **响应延迟** | 最后一个字 → 交出整句文本 | 500–700ms（豆包宣传端到端 87ms 级是模型内部，不是用户感知） | **616ms（短句）/ 920ms（8s 长句）**，实测见 §4 |
| **判停准确率** | 「该停时停、不该停时不停」 | 语义判停 TPR 99.3% / TNR 86.6%（LiveKit 中文） | 后缀词表，无量化 |
| **打断延迟** | 用户插话 → 我们停嘴 | <200ms（全双工 + AEC） | 半双工，靠能量门，300ms 混响期 |
| **首字反馈** | 开口 → 界面有反应 | 有实时字幕 | **无**（离线非流式 ASR 做不出来） |
| **噪声鲁棒** | 咖啡厅/外放还能用 | 专用降噪（Krisp 级） | **无降噪** |
| **稳定性** | 连续开 8 小时不出错 | — | 有自愈重连，无长跑测试 |

**这张表就是验收标准。** 后面每条改动都要能落到某一行上，否则不做。

## 2. 别人怎么做的（可抄的部分）

### 2.1 OpenAI Realtime：把「判停」从声学问题变成语义问题

`server_vad` 是最朴素的做法，参数只有三个（官方文档示例值）：

```json
{"type": "server_vad", "threshold": 0.5,
 "prefix_padding_ms": 300, "silence_duration_ms": 500,
 "create_response": true, "interrupt_response": true}
```

三个参数各自的用途很值得记：

- `threshold`：VAD 触发门限，噪声环境调高。
- **`prefix_padding_ms`：判出人声时往前补 300ms 音频。** VAD 是逐块判的，人声的
  第一个音素往往落在「上一块」里——不补就把起手字削掉。中文里最常被削的正是
  「嗯」「把」「那」这类轻声起头。**这条我们之前完全没有，是纯 bug。**
- `silence_duration_ms`：多久没声音算说完。

`semantic_vad` 换了个思路：用一个**语义分类器**给「用户说完了的概率」打分。

> 概率低 → 等一个超时；概率高 → 不用等。
> —— OpenAI 文档《Voice activity detection》

它多出一个 `eagerness`（`auto`/`low`/`high`，`auto` = `medium`）：
`low` 让用户慢慢说，`high` 尽快切。**这就是「断断续续说怎么办」的官方答案**：
不是调一个静音阈值，而是「先看语义、再决定等多久」。

### 2.2 LiveKit turn-detector：小模型 + 每语言阈值

- 底座 **Qwen2.5-0.5B-Instruct**，先用 7B 教师模型蒸馏，再 INT8 量化成 ONNX。
- 输入：最近 **6 轮对话、截断到 128 token**，用 Qwen chat template 拼；最后一条
  用户消息**不带** `<|im_end|>`。
- 输出：模型预测 `<|im_end|>` 的下一个 token 概率 → 高 = 说完了。
- **每语言一个阈值**（`languages.json`），中文 TPR **99.3%** / TNR **86.6%**。
- 纯 CPU，<500MB 内存。
- 明确写在限制里：**只能吃文本，拿不到语调、停顿、重音**。

这条对我们最有用的是「**每语言单独标定阈值**」这个工程细节——中文的句末语气词
（吗/呢/吧/啊）和英文完全不同，一个全局阈值必然偏。

### 2.3 Pipecat smart-turn v3：直接吃音频，8MB

- 底座 **Whisper Tiny**，加一层线性分类头，约 **8M 参数**。
- INT8 量化后 **8MB**，`10ms`（部分 CPU）～`<100ms`（多数云实例），
  Pipecat Cloud 1x 实测 **65ms**。
- **audio-native**：直接吃 16kHz 单声道 PCM，因此能用上**语调、节奏**这些
  文本模型拿不到的信息。支持 23 种语言（含中文）。
- 用法上有一条很关键的工程约束：**只在 VAD 判出静音之后跑**，输入是「整个这一轮
  的录音」（最长 8s，不够就在**前面**补零）。如果跑的过程中用户又说话了，
  **重跑整段，而不是只跑新增那段**——它需要上下文。

对比一下就清楚了：LiveKit 那条要**先有转写文本**（多一层依赖、多一份延迟），
smart-turn 直接吃音频。**我们本地已经有 VAD 和 PCM，smart-turn 是更短的那条路。**

### 2.4 豆包：端到端 + 动态判停 + 全双工

公开材料能确认的（火山引擎产品页 / 官方新闻）：

- **端到端实时语音大模型**，语音进、语音出，不是「ASR→LLM→TTS」三段拼接。
- 2026 年 4 月升级的 **Seeduplex**：官方描述为「原生全双工端到端语音大模型」，
  能在复杂声学场景下「精准抗干扰与**动态判停**」。
- 流式解码：**每 300ms 输出一次中间结果**（chunk-based）。

**「动态判停」= 语义判停**，和 OpenAI `semantic_vad` 是同一件事的两种叫法。
「端到端」是另一件事：省掉中间两次文本转换，延迟和「机器味」都降。
但端到端模型不可控、不可插工具，**和我们的产品形态（执行命令）冲突**，
所以这条路我们不走——我们走「级联但每一层做到位」。

### 2.5 降噪与回声消除：两个独立问题，别混

| 问题 | 是什么 | 开源方案 | 成本 |
| :--- | :--- | :--- | :--- |
| **降噪 NS** | 去掉环境噪声（空调、键盘、街道） | DeepFilterNet3（单帧 <10ms，模型 ~2.5MB）、RNNoise（480 样本 = 30ms@16k，48 维特征 + LSTM） | 低 |
| **回声消除 AEC** | 去掉「我们自己说的话被麦克风收回」 | WebRTC AEC3（10ms 帧，内部 64 样本块，专门处理双讲） | 中 |

**这两件事不能互相替代**，而且顺序是先 AEC 再 NS。我们现在的 `EchoGate` 是
「TTS 期间把麦克风当静音」——这是**半双工**，本质是「用时间换正确性」：
代价是用户说话时我们在装聋。真全双工必须上 AEC。

## 3. 审计：我们现在到底什么样（有实测）

### 3.1 现有链路（0.1.25 之前）

```
麦克风 512 样本/32ms
  → [可选] AGC + high-shelf（仅 mask_mode）
  → VAD（Silero，逐块）
  → EndpointDetector（静音 800ms / 语义尾词延长 2500ms / 硬上限 12s）
  → 候选态复查：整段重新解码 → should_end(文本)
  → 声纹校验（CAM++）
  → 终稿：整段**再**解码一次
  → 派发
```

### 3.2 实测数据（本机 M 系列，SenseVoice int8，2 线程）

解码耗时随音频长度**线性增长**：

| 音频长度 | 0.5s | 1s | 2s | 4s | 6s | 10s | 12s |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 解码耗时 | 22ms | 35ms | 68ms | 111ms | 138ms | 253ms | 283ms |

由此可以算出**改之前**的端点延迟（最后一个字 → 开始处理）：

| 环节 | 短句（≤2s） | 8s 长句 |
| :--- | ---: | ---: |
| 等静音（`silence_duration_ms`） | 800ms | 800ms |
| 候选态复查：整段解码 | 35–68ms | ~220ms |
| 终稿：**同一段音频再解一遍** | 35–68ms | ~220ms |
| **合计** | **≈ 870–940ms** | **≈ 1.24s** |

### 3.3 逐项问题清单

| # | 问题 | 后果 | 严重度 |
| :--- | :--- | :--- | :--- |
| 1 | **没有 prefix padding** | 起手字被削，「嗯」「把」听不清 | **高（准确率）** |
| 2 | **终稿重复解码**（候选态解一次、终稿再解一次，离线引擎两次结果完全一样） | 白花 35–220ms | **高（延迟）** |
| 3 | **候选态整段重解**，而判停只看结尾 | 长句子上无谓 CPU，且在识别线程里 | 中 |
| 4 | `silence_duration_ms = 800` | 比豆包/ChatGPT 慢一倍多 | **高（延迟）** |
| 5 | 语义判停是**后缀词表**，无量化、无每语言标定 | 判停质量不可测、不可改进 | **高（质量）** |
| 6 | 非流式 ASR | 没有实时字幕；终稿必须等整段；长句线性变慢 | **高（架构）** |
| 7 | 无降噪 | 噪声下 VAD 假阳性、WER 上升 | 中 |
| 8 | 无 AEC，半双工 | 我们说话时用户插不进来 | **高（交互）** |
| 9 | 打断后**不截断已播文本** | 模型以为自己把没播的也说了，后续对话错乱 | **高（正确性）** |
| 10 | 无长跑稳定性测试 | 「能一直开」没有证据 | 中 |

第 9 条值得单独说：OpenAI 的 `conversation.item.truncate` 不只是停播放，
**还会把服务端上下文里那段被截掉的文本一起删掉**，注释原话是
「截断音频会删除服务器端的文本记录，以确保上下文中没有用户不知道的文本」。
我们现在打断只停 TTS，上下文里那段「说了但用户没听到」的话还在——下一次回答会
接着它说，用户会觉得「它怎么答非所问」。

## 4. 已经改掉的（0.1.25）

对应上面第 1–4 条，都是**当天能拿、可测**的：

| 改动 | 依据 | 效果 |
| :--- | :--- | :--- |
| **加 `prefix_padding_ms = 300`** | 抄 OpenAI `server_vad` | 起手字不再被削 |
| **终稿复用候选态解码结果**（仅当引擎声明 `partial_equals_final`） | 本地实测两次解码结果一致 | 短句省 35–68ms |
| **候选态只解最后 3s** | 判停只看结尾 | 长句复查从 O(长度) 降到常数 |
| **`silence_duration_ms` 800 → 500** | OpenAI 文档示例值 500 | 省 300ms |
| **`min_speech_ms` 按人声时长算**（不再按缓冲长度） | 加了 prefix padding 后缓冲必然虚长 | 咳嗽不再凑过门槛 |
| **补语义尾词表**（还有/比如/虽然/为了…） | 中文列举、从属连词 | 少切半截话 |

### 4.1 改后实测（一条命令可复现）

```
$ .venv/bin/python scripts/voice_bench.py endpoint --real
    语音长度       端点白等       判定耗时       产出音频
    0.8s       564ms        52ms      1664ms
    1.2s       548ms        98ms      2048ms
    2.0s       548ms        91ms      2848ms
    4.0s       564ms       261ms      4864ms
    8.0s       564ms       356ms      8864ms

端点白等：p50 564ms  max 564ms（音频长度，与机器无关）
判定耗时：p50 98ms  max 356ms（墙钟，含解码）
（配置：静音 500ms，延长 2500ms，前缀 300ms，复查窗口 3000ms）
```

两列要分开看，别加错了：

- **端点白等**是**音频长度**——纯粹由阈值决定，换台机器、换台服务器都是这个数。
  用户感知到的「我停了」到「它开始动」主要就是这一段。
- **判定耗时**是**墙钟**——解码真正花的 CPU 时间，跟模型、窗口、机器都有关。

| 语音长度 | 端点白等 | 判定耗时 | 用户感知（两者相加） | 改前 | 省了 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 0.8s | 564ms | 52ms | **616ms** | ~844ms | 228ms |
| 2.0s | 548ms | 91ms | **639ms** | ~870ms | 231ms |
| 8.0s | 564ms | 356ms | **920ms** | ~1240ms | 320ms |

短句已经落进 500–700ms 这个「像人」的区间。**长句还没有**，原因下一节说。

### 4.2 长句还差的那 350ms：一次纯浪费的解码

8s 那一行的判定耗时 356ms，比 3s 音频该有的 ~90ms 高得多。查下来是这样：

```
静音到 → 解最后 3s（~90ms）→ 判出「说完了」
       → 但尾部文本不完整，不能当终稿 → 丢掉
       → 解全段 8s（~260ms）→ 终稿
```

**尾部那次解码对长句是纯开销**：它只为了回答「说完了吗」，答完就扔。
短句不会有这个问题（尾巴就是全段，结果直接复用），所以这个浪费只出现在
长句上——而长句恰恰是等得最久的那种。

这也正是 §6.1 要换 smart-turn 的**量化理由**：判停用吃音频的模型，
就不再需要「为了判停先解码」，长句的 356ms 直接掉到 ~260ms。
不是「换个更准的模型」，是**砍掉一条依赖**。

> 一个教训记在这里：第一次实现「复用候选文本」时，条件只写了「文本非空」，
> 忘了检查引擎是否真的 `partial == final`。脚本回放引擎（`final=True` 才推进队列）
> 的 peek 结果被当成终稿，**同一句话被反复派发**。被 `test_e2e` 当场逮住。
> 这类「省一次调用」的优化，必须带一个「谁有资格省」的显式契约。

> 另一个更阴的：`EndpointDetector.deadline_ms` 是 dataclass 默认值 800，
> 只有 `reset()` 才把它设成配置里的 `silence_ms`。而 `reset()` 只在收尾时调用——
> **配置里的静音阈值对第一句话根本不生效**。改完配置一测还是 852ms，才发现的。
> 这个 bug 读代码看不出来，是 `voice_bench.py` 量出来的：`__post_init__` 里补一次
> `self._ep.reset()` 之后才变成 564ms。**所以这个脚本不是文档附件，是工具。**

## 5. 目标架构

```
                    ┌──────────────── 采集 32ms ────────────────┐
                    ▼                                          │
         ┌── AEC3（拿 TTS 播放流做参考）──┐                      │
         │   双讲检测：用户说话时不做抑制   │                      │
         └──────────────┬───────────────┘                      │
                        ▼                                        │
              DeepFilterNet3 降噪（<10ms/帧）                     │
                        ▼                                        │
                 AGC（固定目标 -3dBFS）                           │
                        ▼                                        │
              Silero VAD（逐块，1ms 级）                          │
                        ▼                                        │
        ┌──── 静音 300–500ms ────┐                               │
        │  触发 turn detector    │                               │
        │  smart-turn v3（8MB）  │◄── 整轮 PCM（≤8s，前补零）      │
        │  → 说完了？概率 p      │                               │
        └────────┬──────────────┘                               │
                 │ p 高 → 立刻切                                    │
                 │ p 低 → 再等（eagerness 语义，最多 2.5s）           │
                 ▼                                                │
        流式 ASR（边说边出字）────► 实时字幕（胶囊）                 │
                 │ 终稿                                          │
                 ▼                                                │
              意图路由 → 工具 / LLM                                │
                 ▼                                                │
        流式 TTS（首字节 200–400ms）──► 播放 ─────────────────────┘
                 │
                 └─ 被打断 → 停播 + **截断上下文里未播的文本**
```

三条和现在不同的地方，按重要性排：

1. **流式 ASR**（解决「没有实时反馈」和「长句线性变慢」）
2. **audio-native 判停模型**（解决「判停质量不可测」）
3. **AEC + 真双工**（解决「插不进去话」）

## 6. 选型：买什么、抄什么

### 6.1 判停（turn detection）—— 先抄这个，最划算

| 方案 | 形态 | 中文 | 延迟 | 依赖 | 结论 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Pipecat smart-turn v3** | 8MB int8 ONNX，吃 PCM | ✅ | 10–65ms | onnxruntime（已有） | **首选** |
| LiveKit turn-detector | Qwen2.5-0.5B INT8，吃文本 | ✅ TPR 99.3% | CPU | 需要先有 STT 文本 | 备选 |

选 smart-turn 的理由不是「它更准」，而是**它不依赖 STT**：我们现在的候选态复查
必须先解码才能判停，等于「为了决定要不要停，先花 90ms 解码」。换成吃音频的模型，
这一步的依赖就断了，判停可以在 VAD 判出静音的瞬间开始，和「解码」并行。

按 §4.1 的实测，这一换能拿到两笔钱：

1. 砍掉长句那次纯浪费的尾部解码 —— **~96ms**（8s 长句 356ms → ~260ms）
2. 有了语义判停兜底，静音阈值可以从 500ms 再降到 300ms —— **~200ms**

两笔加起来，短句 ~616ms → **~420ms**，长句 ~920ms → **~620ms**。
这是唯一一条能让我们**追平**（而不只是接近）豆包/ChatGPT 的改动。

许可证是 BSD-2，可商用。

### 6.2 识别（STT）

| 方案 | 流式 | 中文 | 隐私 | 结论 |
| :--- | :--- | :--- | :--- | :--- |
| sherpa-onnx **streaming** zipformer / paraformer | ✅ | 好 | 不出网 | **默认**（和现有模型管理复用） |
| 现有 SenseVoice（离线非流式） | ❌ | 好 | 不出网 | 保留为兜底 |
| 云端流式 ASR（火山/阿里/腾讯） | ✅ | 最好 | 出网 | 可选开关 |

**建议**：本地流式为主，云端流式为可选。理由：我们是「常开监听」的产品，
把每一句话都传云端，隐私账算不过来；而流式 zipformer 在中文命令句上的准确率
已经够用（命令句短、词汇集中，还能加热词）。

### 6.3 合成（TTS）—— 明天要买的那个

关键不是「哪个最好听」，是**首字节延迟**和**是否真流式**。常开助手最怕
「想 2 秒才出声」。

| 方案 | 流式首字节 | 中文自然度 | 备注 |
| :--- | :--- | :--- | :--- |
| **豆包语音合成 2.0**（火山） | 低（官方主打低延迟流式） | 最好之一 | 支持声音复刻；和豆包语音同源，风格一致 |
| MiniMax speech-02 | 低 | 很好 | 情绪表现强 |
| Azure / OpenAI TTS | 中 | 一般 | 中文语调偏「播音腔」 |
| **CosyVoice2**（开源，可自托管） | 中 | 好 | 免费、可离线，作为降级路径 |

**建议**：买**豆包语音合成 2.0 流式**。理由：中文自然度第一梯队、支持流式、
支持声音复刻（将来做「你自己的声音」不用换供应商）。工程上要做的三件事：

1. **按句流式**：LLM 一产出第一个句子就送 TTS，不等全文。
2. **首字节超时降级**：>1.5s 没出首字节就切备用供应商，别让用户干等。
3. **保留本地兜底**：`say` / CosyVoice 自托管，断网也能出声（现在已有 `say`）。

### 6.4 降噪 / AEC

| 用途 | 方案 | 备注 |
| :--- | :--- | :--- |
| 降噪 | **DeepFilterNet3** | 单帧 <10ms、模型 ~2.5MB，有 Python 包 |
| 降噪（轻量备选） | RNNoise | 30ms 帧、48 维特征 + LSTM，CPU 几乎零成本 |
| 回声消除 | **WebRTC AEC3** | 唯一成熟的开源选择；Python 绑定麻烦，建议用一个小 native 进程 |

AEC 的工程难点不在算法，在**时钟对齐**：必须拿到「实际播放出去的采样」作为参考
信号。macOS 上要换 `AVAudioEngine` 的 voice-processing IO，或者用
`kAudioUnitSubType_VoiceProcessingIO`——这会牵动 `MicSource` 的实现，是本次
路线图里工作量最大的一块。

### 6.5 一句话决策：买什么、装什么、不做什么

用户问的是「要做到接近豆包/ChatGPT，该用哪个模型的 API、架构怎么设计」。
把上面四节压成一张表：

| 环节 | 决定 | 为什么不是别的 |
| :--- | :--- | :--- |
| **判停** | 本地 **Pipecat smart-turn v3**（8MB int8 ONNX，BSD-2） | 唯一 audio-native 且不依赖 STT 的方案；LiveKit 那条要先有文本，等于没解决问题 |
| **识别** | 本地 **sherpa-onnx streaming zipformer**，SenseVoice 留作兜底 | 常开监听不能把每句话传云端；命令句短、能加热词，本地够用 |
| **合成** | **豆包语音合成 2.0 流式**（明天买），CosyVoice2 / `say` 兜底 | 中文自然度第一梯队 + 支持声音复刻，将来换声音不用换供应商 |
| **降噪** | **DeepFilterNet3**（P2） | 单帧 <10ms，CPU 成本可忽略；RNNoise 作为更轻的备选 |
| **双工** | **WebRTC AEC3**（P2，要改音频 IO） | 唯一成熟开源实现；没有它就永远是半双工 |
| **不做** | **端到端语音大模型**（豆包那条路） | 不可控、不能插工具，和「执行命令」的产品形态直接冲突 |

架构上我们走「**级联，但每一层做到位**」：`VAD → 判停模型 → 流式 ASR → 意图/LLM → 流式 TTS`。
端到端省掉的是中间两次转换，代价是失去可控性——**对我们这个产品是亏的**。

要买的只有一样东西：**TTS**。其余全在本地，都能离线跑，都是可商用许可证。

## 7. 参数与阈值：给值，也给理由

| 参数 | 现值 | 建议 | 依据 |
| :--- | ---: | ---: | :--- |
| `chunk_size` | 512（32ms） | 512 | 再小 VAD 调用次数翻倍，收益不明显 |
| `vad_threshold` | 0.5 | 0.5（安静）/ 0.6（噪声） | 噪声下提高阈值；应做成自适应 |
| `prefix_padding_ms` | 300 | **300** | 抄 OpenAI |
| `silence_duration_ms` | 800 → **500** | 500（现在）/ **300**（上判停模型后） | 500 是 OpenAI 示例值；300 需要语义判停兜底，否则会切半截 |
| `endpoint_extend_ms` | 2500 | **2500**（命令）/ 1200（问答） | 对应 OpenAI `eagerness` |
| `partial_window_ms` | — → **3000** | 3000 | 判停只看结尾 |
| `min_speech_ms` | 200 | **200**（按人声时长） | 再低会把咳嗽放进来 |
| `max_utterance_ms` | 12000 | 12000 | 单条命令的上限，不是对话上限 |
| `voiceprint_threshold` | 0.75 | 0.75（真麦）/ 0.80（合成语料） | 见 `docs/ACCEPTANCE.md` 的标定记录 |
| `echo_decay_ms` | 300 | 300（半双工）→ 0（上了 AEC 之后） | AEC 生效后不再需要时间门 |

**「断断续续说」的处理**（用户明确问的）：

1. 静音 500ms → 进入**候选端点**，不是立刻切。
2. 候选点做语义判断：结尾是「然后/比如/虽然…」→ 判为「没说完」。
3. 没说完 → 把截止时间延到 2500ms，继续收；期间用户又开口，静音计数清零。
4. 2500ms 还没动静 → 认定说完了，走终稿。
5. 硬上限 12s 强制收尾（防一直说不停）。

这套是**「声学定候选、语义定终局」**，和 OpenAI `semantic_vad` 同构，
只是把「语义分类器」换成了后缀词表——**这就是第 5 条要换模型的原因**。

## 8. 路线图

| 优先级 | 事项 | 预期收益 | 工作量 | 风险 |
| :--- | :--- | :--- | :--- | :--- |
| **P0 已完成** | prefix padding / 省重复解码 / 尾部窗口 / 静音 500 | 实测省 228–320ms（§4.1），起手字不丢 | 已做 | 低 |
| **P1** | **smart-turn v3 判停** | 判停可量化；短句 ~616→420ms，长句 ~920→620ms | 1–2 天 | 中（新模型下载） |
| **P1** | **流式 ASR** | 实时字幕；长句不再线性变慢 | 3–5 天 | 中 |
| **P1** | **TTS 流式 + 首字节降级** | 出声快 1–2s | 1–2 天（拿到 API 后） | 低 |
| **P1** | **打断时截断上下文** | 修「答非所问」 | 0.5 天 | 低 |
| **P2** | **DeepFilterNet3 降噪** | 噪声下 WER 明显下降 | 2 天 | 中 |
| **P2** | **AEC3 + 真双工** | 能插话 | 5–8 天 | **高**（要改音频 IO） |
| **P2** | 长跑稳定性测试（8h） | 「能一直开」有证据 | 1 天 | 低 |

**为什么 AEC 排 P2 而不是 P1**：它依赖换音频 IO（`VoiceProcessingIO`），
会同时影响采集、播放、TTS 三条路。在流式 ASR 和判停模型都到位之前做它，
等于在一个还要大改的管线上做最贵的改动。

## 9. 怎么验收「丝滑」

不能靠感觉。`scripts/voice_bench.py` 已经在跑第一项，其余四项随 P1 落地：

| 指标 | 测法 | 目标 | 现状 |
| :--- | :--- | :--- | :--- |
| 端点延迟 | 合成音频「说话 + 静音」，量最后一个语音帧到 `Utterance` 产出 | p95 < 700ms | ✅ **616ms**（短句）/ 920ms（8s 长句），`voice_bench.py endpoint --real` |
| 判停 TPR/TNR | 用带标注的「说完 / 没说完」音频对，跑判停器 | TPR > 98%，TNR > 85% | ⬜ 需 smart-turn |
| 起手字保留 | 合成一个以轻声开头的词，看转写是否完整 | 100% | ⬜ 需语料 |
| 打断延迟 | TTS 播放中注入人声，量到停播 | < 200ms | ⬜ 需 AEC |
| 长跑 | 8h 循环喂音频，看内存/线程/队列 | 无增长、无堆积 | ⬜ 需长跑脚本 |

**用法**（`--real` 才是真数字，不带它跑的是脚本回放，只看分段逻辑对不对）：

```bash
.venv/bin/python scripts/voice_bench.py endpoint            # 秒出，验证分段逻辑
.venv/bin/python scripts/voice_bench.py endpoint --real      # 含解码墙钟，看真延迟
```

改任何阈值、换任何模型，先跑这一条再说话。**上面 §4.1 的每一个数字都来自它。**
