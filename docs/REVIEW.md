# 产品与工程审查（REVIEW）

> 审查时间：2026-10-27｜方法：**抽查，不通读**。真起服务、真发跨站请求、真测延迟、真改配置，
> 不看"文档说它应该怎样"。结论分三类：已修 / 未修（附风险）/ 不打算修（附理由）。

## 1. 一句话结论

功能闭环是通的，但**产品的"入口"和"第一次使用"是断的**：一个陌生页面能直接命令它干活，
而一个真人第一次装上它，只会看到一句"先运行 voxos enroll"然后进程退出。这轮把这两头补上了。

### 关于第 1 条，为什么它最严重

这个产品的全部卖点是"危险操作在架构上不可能发生"。红线网关把关的是**工具**，
但**入口**是裸的：任何本地页面（包括你正在浏览的任意网站）都能发一个 simple request 过来。
`fetch('http://127.0.0.1:8765/command', {method:'POST', body:'把 README 改成...'})`
—— 不需要 CORS 预检，因为 `text/plain` 属于简单请求；服务端也没校验 `Origin`。
**安全边界画在了门后面。**

现在的模型（`REDLINES.md §6`）：只有页面本身免令牌；其余全部要本次运行的随机令牌，
且拒绝非本机同源的 `Origin`。令牌在服务端渲染页面时注入，跨站页面读不到它（同源策略挡着）。

## 4. 设计取舍（为什么是现在这个样子）

**为什么不做主窗口。** 语音助手的价值是"不用看屏幕"。一旦有了主窗口，产品就会开始争夺注意力：
未读红点、历史列表、推荐操作 —— 这些是聊天机器人的形态，不是操作系统的形态。
张小龙讲的"用完即走"在这里的具体含义是：**你说话，它做事，胶囊闪一下，然后它消失。**

**为什么设置放在展开态而不是独立页面。** 设置是低频动作，但它必须"伸手可及"。
独立页面意味着用户要记住一个 URL 或找一个入口；展开态意味着"它就在那儿"。
代价是信息密度受限，所以只放 19 个真正会改的字段，其余留在 TOML 里给愿意读文件的人。

**为什么保留"最近 8 条"。** 语音产品最大的信任缺口是"我明明说了"。
不给回看，用户就无法判断是麦克风、声纹、识别还是路由的问题。这一条不是功能，是排错基础设施。

**为什么危险字段标「重启生效」。** 端口、识别后端、面罩模式改了要重建管道。
假装能热更，只会让用户以为改坏了。**说清楚比做得漂亮重要。**

## 6. 这一轮新增的验收项

从 10 项扩到 **14 项**，新增的四项都是"抽查出来的坑"，不是凑数：

1. **跨站 / 无令牌请求被拦截** —— 401 / 403 / 200 三个码都要对，且被拒的请求**一次都不能执行**。
2. **上下文注入不阻塞派发** —— p95 < 5ms（修复前是 271ms）。
3. **设置写回保住注释** —— 改值、保注释、写到 `--config` 指定的文件、非法值一个字节都不写。
4. **无声纹时给出录入入口** —— 不再是"打印一行然后退出"。

## 12. 换成 CDP 驱动（`scripts/shot.py`）

自己写了个 120 行的 WebSocket + CDP 客户端（零依赖），能精确设视口、执行页面自己的函数、
派发鼠标事件、按元素裁切。截图从此是**可复现的检查**，不是一次性的运气。

三个环境坑，记下来免得再踩：
- Chrome 在受限环境里必须 `--no-sandbox`，否则 network service 反复崩溃、DevTools 连上就断。
- 访问 `127.0.0.1` 必须绕开系统代理（否则拿到代理的 502），`urllib` 要用空 `ProxyHandler`。
- 别同时用 `--force-device-scale-factor` 和 `clip.scale`，会得到 2.29 倍这种鬼比例；
  只留 `deviceScaleFactor`，`clip.scale=1`，输出就正好是 2 倍宽（840px）。

# 第四轮：把「没做」逐条做掉（2026-10-28 凌晨）

上一轮结尾列了三条没做的：真实 STT、真人声纹、8 小时长稳。这一轮把能做的做完，

## 15. 真实 STT 接上了，也量出了它到底行不行

SenseVoice-Small int8（sherpa-onnx，229MB）接进 `audio.py`，设置页切
`stt.backend = sense_voice` 即用，缺模型时退回 `scripted` 而不是崩。

实测：24 句 TTS 语料 / 818 字符 / 6 个音色。

| 指标 | 实测 |
| :--- | :--- |
| 字符错误率（总体） | **2.8%** |
| 中文 | 1.4%（8 句 142 字，只有 1 句有差异） |
| 英文 | 3.1%（16 句，按字符算） |
| 实时率 | **33–38× 实时**（2.1–2.4s 处理 79s 音频，单次有抖动） |

两件必须说清楚的事：

1. **中文那 1.4% 不是错。** 唯一有差异的是「明天上午十点」→「明天上午10点」——SenseVoice 的
   withitn 逆文本规范化在把中文数字转阿拉伯数字。按字面算错 2 个字符，按语义算是 0 个。
   中文的真实错误率是 **0**。
2. **英文 3.1% 是字符级，会骗人。** 按词算是 **12.5%（21/168）**：`null` → `Ill` / `and I'll`、
   `auth` → `Oth` / `o` / `author`、`dev` → `Dave`、`login timeout` → `log and time' out`。
   这组英文是 Samantha / Daniel / Karen / Moira **四个英文音色**读的（核过 manifest），
   也就是说：**母语发音下这些短术语照样错**，不是中式口音的问题。
   那中式口音下会怎样？见 §22——同一批术语换成中文音色，召回掉到 29.4%。
   **这两组数字一起证明热词注入（Task 2.3）不是可选项**：代码术语必须走热词表，
   不能指望声学模型自己扛。

顺带把 `fetch_models.py` 改成「ASR 模型缺失只警告不失败」——它是可选的，缺了就退回 `scripted`。

## 16. 派发延迟差 63 倍，查下来是环境

这一轮验收先跑出端到端 p95 = **23.4ms**，而上一轮记录的是 0.90ms。差 26 倍，必须查。

查下来是环境，不是代码：那次运行的 `open()` 被沙箱代理到宿主进程（`sitecustomize.py`
的 `_brokered_open`），单次 `write_text` 要 **10.2ms**、`mkdir` 4.6ms。而「写日志」这条链路
要写两个文件（日志 + 审计），17ms 正好对上。

后来同一条命令换到没有代理的 shell 里再跑，同一项变成 **0.371ms**。**63 倍，代码一个字没改。**

| 环节 | 沙箱代理 I/O | 无代理 |
| :--- | ---: | ---: |
| 快通道路由决策 | 0.0008ms | 0.0008ms |
| 上下文注入 | 0.007ms | 0.005ms |
| 端到端（含两次落盘） | 23.4ms | **0.371ms** |
| 一次 `write_text` | 10.2ms | — |

关键不是哪个数好看，而是**前两项两次几乎一样**——它们不碰文件系统。差异只出现在落盘那一段，
这才能把结论钉死在"文件 I/O"上，而不是"机器当时有点忙"。

## 18. 截图工具的第三课：headless Chrome 不产帧

给撤销按钮量宽度时撞上一个鬼故事：`.btn.sec` 规则明明命中（`matches()` 返回 true、
`cssRules` 里也翻得到），`getComputedStyle` 却死活返回旧值——连注入
`#reset{flex:0 0 auto !important}` 都压不住，我一度以为撞上了浏览器 bug。

真相是 CSS `transition: .15s`。headless Chrome 不主动产帧，动画时钟不走，过渡永远停在起始值；
`getComputedStyle` 和 `getBoundingClientRect` 读到的都是**改之前**的样子。逼出一帧
（随便截一张图）之后，三个按钮立刻回到 84 / 84 / 174。

修法：`shot.py` 加 `settle()`，截图前先用两张 quality=1 的 jpeg 把动画时钟推过去。

同一个坑还咬了第二口：`.stage:has(.confirm:not([hidden])) .panel{max-height:calc(100vh-200px)}`
这条规则（确认卡出现时把面板压矮，好让卡片留在窗口里）在 `getComputedStyle` 里读到的永远是
`550px`（未压缩的值），要逼出一帧才变成 `420px`。**也就是说，在真机上它是好的，在截图里它是坏的**——
如果我只信截图，就会去改一条根本没问题的规则。

上一轮的教训是「截图会骗人，量出来的数不会」。这一轮得补两句：
**量出来的数也会骗人，如果渲染管线没走完**；而且**"逼一帧"必须成为测量前的固定动作**，
不然同一个坑会用不同的样子反复出现。

### 第四课：headless 默认就在"减弱动效"里

第五轮给倒计时补守卫时发现的。写了一条「减弱动效时装饰该停、但倒计时不能停」的
检查，注入回归时它红了——可它红的方式不对：**连正常状态那半也红了**。

查下去是这样：

```javascript
matchMedia('(prefers-reduced-motion: reduce)').matches   // true
// 设成 no-preference → false；清空覆盖 → 又变回 true
```

**headless Chrome 默认报 `reduce`。** 两个后果：

1. 我那条检查只量了 reduce 状态，而 reduce 是默认状态——把 `animation` 全写成
   `none` 它也能通过。改成**两个状态都量**（差分）之后才有意义：
   正常 `倒计时=drain / 装饰=pulse`，减弱 `倒计时=drain / 装饰=none`。
2. 更值得注意的是：**之前拍的 10 张界面截图，全都是在减弱动效下拍的。**
   也就是说 `breathe`（呼吸点）、`pulse`（电平条）从来没在任何一张截图里动过。
   布局测量不受影响（尺寸与动画无关），但"动效看起来对不对"这件事，
   之前其实**没有真正看过**——只是文档里写着它应该有。

这跟第三课是同一类：工具给的"看起来正常"和"实际正常"是两回事。差别在于
前两次骗人的是**帧**，这次骗人的是**默认值**——一个连开关都没拨过的状态。

## 19. 设置撤销：只退一步，退完就没了

`settings.bak` 存在配置文件旁边的 `.voxos/` 里（跟着 `--config` 走，不污染仓库根）。
保存前留一份，撤销时写回去，然后把备份删掉。

- 只退一步是刻意的：配置不是代码，多级撤销没人用，还会让"现在到底是什么状态"变模糊。
- 退完按钮就消失（`/api/settings` 带 `undo` 字段），不留一个点了没反应的灰按钮。
- 备份写成功才删，写失败备份还在——撤销失败不该把退路也弄丢。

端到端验过：`0.82` → 保存 `0.90` → 备份里是 `0.82` → 撤销 → `0.82` → 备份没了 →
再撤销返回 409「没有可撤销的保存记录」。

## 21. 一声咳嗽就能把管道永久拖死（#33）

长稳脚本第一次跑出来是这样的：

```
    分钟   RSS(MB)    CPU%         块     语音段
   0.2     173.4     1.1        51       0
   ...                           每块 20ms 音频，51 块/秒 = 实时
   0.2     149.7    15.8       615       0     ← 12.2 秒处
   0.3     153.3    56.4       644       0
   0.4     158.8    95.0       692       0
```

前 12 秒 51 块/秒、CPU 1%；到第 609 块（**正好 12.2 秒**）之后掉到 7 块/秒，
CPU 一路爬到 95%，再也没回来。

12 秒就是 `audio.max_utterance_ms`。追进去看：VAD 判了硬上限 `force_end`，
`_finalize()` 里转写为空 → `return None` → `run()` 把 `None` 理解成
「半截话，继续收音，不清缓冲」→ 下一块音频进来，`_maybe_finalize()` 又把
**整个缓冲重新拼一遍再解码一遍**。缓冲只增不减，每块都比上一块更贵。

真机上的触发条件普通得可怕：一声咳嗽、一次 VAD 假阳性、一句被回声门吞掉的话——
任何一次「有人声但转写为空」都会把管道锁死，直到进程重启。

修法：`_finalize()` 改成**永远返回一个 Utterance**，空转写返回
`Utterance("", …, False, reason="空转写，已丢弃")`。返回 `None` 的语义收窄成
「候选态还没说完」，硬上限不再走这条路。

回归测试 `test_force_end_flushes_even_when_transcript_is_empty`：6 秒连续人声、
转写恒为空，要求至少收尾 4 次。把修复退回去，这条测试**跑 117 秒才失败**
（6 秒音频，19× 退化）——测试本身就把病征复现了一遍。

修完：50 块/秒 = 实时，CPU 稳定 3.1%。

## 22. 「87.5%」测错了对象（#34）

上一轮报的「英文词级 87.5%」是在 `EN_LINES` 上量的：

```python
EN_LINES = ("add a null check in the auth module and run the tests", ...)
```

这是**英文句子**，用**英文音色**读。它量的是「英文识别能力」，不是「中英混说」。
中文开发者的真实说法是「把 redis 的连接池调大一点」——中文句子里夹术语。

换成真正混说的 10 句（中文音色读，中文句子里夹 17 个术语）重新量：

| 语料 | 念法 | 英文术语 |
| :--- | :--- | ---: |
| `EN_LINES`（英文句子） | 英文音色 | 87.5% |
| `MIXED_LINES`（中文句子夹术语） | 中文音色 | **29.4%** |

差三倍。而且不是模型的锅——做一次对照就清楚了：把同一批混说句子交给**英文音色**读，
`docker`、`build`、`review`、`merge request` 全部识别正确（中文部分因为音色不会说
中文而被整段丢掉）。**同一个模型、同一批术语，念法一换就从 29% 变成全对。**

所以结论是两句话，都得说：

1. 现在这个数字是 29.4%，不是 87.5%。原数字不该再被引用。
2. 29.4% 是「中文音色念英文」的成绩，真人口音落在中文音色和英文音色之间，
   没有真人样本就标定不了——这跟「真人声纹未标定」是同一个卡点。

中文本身没坏：同一批句子的中文字错率 9.6%，链路是通的。

**那补个热词表能不能救回来？** 试过了，不能。给一份**装齐全部 17 个正确术语**的完美词表，
按编辑距离 ≤ 2 匹配，天花板是 **35%（6/17）**：

| 期望 | 听成 | 距离 |
| :--- | :--- | ---: |
| `merge` | `mer` | 2 ✅ |
| `redis` | `read` | 3 |
| `nginx` | `in` / 整段丢失 | 3 / ∞ |
| `python` | `Pon` | 3 |
| `gzip` | `in` | 3 |
| `json` / `yaml` | `um` | 4 / 3 |
| `docker` | `care` | 5 |
| `git` + `rebase` | `gtreadbase` | 9 / 4 |
| `token` | 整段丢失 | ∞ |

错得这么远，不是匹配算法的问题，是声学模型根本没把这几段音听成英文。硬纠只会把
`read` 这种本来就对的词改错。**所以这一轮不加热词表**——写一个只能从 29% 挪到 35%、
还会带来误纠风险的功能，不如把这个结论写清楚，等一个真有热词偏置接口的双语模型。

验收表里这一项标成 **GAP**（未达标、非回归），不塞进 SKIP 假装不存在，
也不让它把「有没有退化」这个信号淹掉。

## 24. 两个会误导判断的工具坑

这一轮我差点得出「确认卡没有倒计时」的错误结论。原因是这条命令：

```bash
grep -n "countdown\|Countdown\|超时\|timeout" web/pill.html   # 零输出，退出码 0
grep -n "Countdown" web/pill.html                             # 两条命中
```

第一反应是「模式里带中文所以不匹配」。做了对照才定下真因：

```bash
printf 'alpha\nbeta\n' > g.txt
grep -c "alpha\|beta" g.txt     # 0   ← 连纯英文都不匹配
grep -cE "alpha|beta" g.txt     # 2
```

这个环境里的 `grep` 是 **toybox 0.8.13**（沙箱的 shim，既不是 GNU 也不是 BSD），
基本正则不支持 `\|` 交替——**而且不报错**，只是零输出、退出码 0。

两个教训：

1. 用 `grep -E` 或 `-e` 多次，别用 `\|`。
2. 更重要的是：**搜索无结果时，先确认搜索本身有效**。一条肯定命中的短模式做对照，
   比相信一个空结果便宜得多。我上一轮刚写过「数字要能被解释」，这一条同样适用于
   工具输出——零结果不是证据，是一个待验证的断言。

### 同类的第二个坑：`make test` 突然 90 个用例报错

跑全量测试，71 passed、**90 errors**，报的全是同一个东西：

```
PermissionError: EEXIST: file already exists,
  mkdir '/private/var/folders/.../T/pytest-of-unknown'
```

第一反应是「pytest 的临时目录残留，清掉就行」。但报错不是 `FileExistsError`，
是 **`PermissionError`**——来自文件代理（`sitecustomize.py` 的 `_brokered_open`），
它把「目录已存在」这种正常情况当成越权拒绝了。也就是说：**测试一行没改，
是环境的文件代理换了脸色**。`mkdir` 一个已存在的目录，在正常系统上 pytest 自己
会处理，在这里变成了整轮失败。

修法不是删目录（下次还会长出来），是把临时目录钉在仓库里：
`pytest --basetemp=.voxos/pytest-tmp`，写进 `Makefile`。

教训跟上面那条同源：**报错信息里那个"操作"和"真因"经常不是一回事。**
`EEXIST` 是现象，`PermissionError` 才是线索——它告诉你问题不在 pytest。

## 25. 长稳：第一版量错了指标

第一次跑 25 分钟，输出是这样的：

```
   分钟   RSS(MB)    CPU%         块     语音段
   1.0     364.4    11.3      3011       9
   2.0     115.1    12.1      6012      18
   5.0      28.2    13.1     15009      46
   8.0     319.4    13.1     24002      74
  25.0     239.6    12.3     75003     230
```

RSS 在 **28MB 和 364MB 之间来回跳**。28MB 比一个裸 Python + numpy 进程（35.7MB）还低，
而它肚子里装着一个 229MB 的模型。这不是"内存很省"，是**读数选错了对象**。

同一台机器、同一份模型，两个指标一起看：

| 时点 | RSS | `phys_footprint` |
| :--- | ---: | ---: |
| 加载前 | 35.7 | 23.0 |
| 模型加载后 | 558.2 | 555.7 |
| 解码 1 次后 | 562.2 | 557.1 |
| 解码 3 次后 | 562.0 | 557.2 |

`resident_size` 数的是「此刻有多少页还留在物理内存里」。模型权重是 mmap 进来的
文件页，内存一紧内核就把它们回收掉，RSS 立刻掉到几十 MB，用的时候再缺页读回来。
**拿 RSS 判泄漏，量到的是页缓存命中率。**

改成 `phys_footprint`（活动监视器里「内存」那一列，含已压缩页），才是「这个进程
到底占了多少」。解码 3 次它从 555.7 走到 557.2——稳定、单调，能判泄漏。

顺带一个真会崩的坑：`proc_pid_rusage` 没有长度参数，内核按自己的结构体写满。
照 `rusage_info_v4` 精确开 80 字节的缓冲，第一次调用就 **段错误（exit 139）**。
给 1KB，只按偏移 72 取 `ri_phys_footprint`，不建模整个结构体。

换成 `phys_footprint` 之后重跑同样的 25 分钟，同一条命令、同一份语料：

```
   分钟    内存(MB)    CPU%         块     语音段
   1.0     406.7    11.1      3006       9
   2.0     406.7    11.4      6011      18
  13.0     407.0    11.8     39004     120
  17.0     407.0    11.7     51007     156
  20.0     407.4    11.7     60013     184
  25.0     407.5    11.7     75001     230
```

| 指标 | 实测 |
| :--- | :--- |
| 时长 | 25.0 分钟（75001 块 = 25 分钟音频，实时节奏） |
| 内存 | 406.7 → 407.5 MB，**跨度 0.8 MB** |
| 斜率 | 全程 +2.0 MB/小时｜后半程 +2.5 MB/小时 |
| CPU | 11.1–12.0%，均值 **11.7%**（单核的 0.12 核） |
| 语音段 | 231 段，全部被声纹锁接受，**拒绝 0** |

怎么读这 0.8MB：它不是连续爬升，而是在 407.0 上停了 7 分钟，然后跳 0.4MB、
再跳 0.1MB——是分配器按块要页，不是每句话漏一点。所以**「2.5 MB/小时」这个
外推不该被引用**：0.8MB 的基数撑不起小时级外推，八小时也就十几 MB，落在噪声里。

它能证明的是：**排除「分钟级就涨几百 MB」这类粗泄漏**，以及管道在 25 分钟里
没有出现缓冲堆积（块数与时间严格线性：75001 块 / 25 分钟 = 50 块/秒 = 实时）。
它不能证明的是八小时不涨——那需要真的挂八小时，且不含设备层（插拔/蓝牙/休眠）。

CPU 这一项也顺带把 §21 的修复钉死了：修之前一声咳嗽之后是 95% 且不回落，
现在是 11.7% 全程平稳。

## 27. 语音认错字之后，动作还发得出去吗

混说术语召回只有 29.4%，上一轮的结论是「模型不行」。但产品的问题从来不是字对不对，
是**动作发不发得出去**。把 10 句混说的真实转写直接喂给路由：

```
把read的连接时调大一点。        → ignore
帮我review一下这个mer request。  → ignore
care镜像重新build一下。         → ignore
in的配置里加上excip。           → ignore
这个SQL查询太慢了。             → ignore
解析改成UM。                    → ignore
用gtreadbase把提交压一下。       → ignore
接口返回502，看一下日志。        → append_structured_log   ← 错
Pon脚本里import报错。           → ignore
把抽过期时间改成2小时。          → ignore
```

9 条 ignore 里 8 条是对的：`docker build`、`sql 慢查询`、`git rebase` 本来就不在
这 4 个工具的能力范围内。**「没有这个能力」不能算成「识别失败」**——把这两件事混在
一起，就会为了让数字好看去加一堆用不上的路由。

真正的问题只有一条，但那条比 ignore 糟得多。

### 读日志被当成了写日志

`heuristic_plan` 只要句子里出现「日志」两个字就判成写日志。于是「看一下日志」
「日志在哪」「把日志清理一下」全都会往日记里写一条——读和写是相反的动作，
用户想查日志，系统给他记了一笔。

根因是把**名词**当成了**意图**。修法是要动词：

```python
_WRITE_LOG = re.compile(
    r"(?:写|记)(?:一?[条个下])?(?:开发|今天的)?日志|记录|记一下|记一条|记个")
```

顺带挖出同一类问题的第二条：运维快通道把服务器名词写成了**可选**——

```
(?:检查|看看|巡检|查一下)(?:一下)?(?:服务器|系统|线上|磁盘|容器)?…
```

于是「看看」+ 任何东西都能命中，「看看今天的日志」去查了服务器负载。名词改成必需，
并补上负载 / 流量 / 监控 / 内存。

### 中文的「删掉」在红线里是空白

「删掉 auth.py」被路由到 `dispatch_code_session`（YELLOW，不弹确认），也就是
**一句话就把删除指令送进了一个正在运行的 coding CLI**。

红线表里 11 条全是命令式写法：`rm -rf`、`drop table`、`git push --force`。
语音用户不会这么说，他说「删掉」「清空」「格式化」——一条都没覆盖。

修法是给红线表加一层 `[confirm]` 词表：工具本身是 YELLOW，但参数里出现不可逆
动作就升级为二次确认。

```toml
[confirm]
'删(掉|除|库|表|文件|了)' = "删除"
'清空' = "清空"
'git\s+push' = "推送到远端"
```

只作用于 YELLOW，这点是刻意的：GREEN 工具改不了东西，不该因为「记录：今天删了
旧接口」这种措辞被拦。确认卡问多了，人就会习惯性点允许，那它跟没有一样。

代价也写清楚：写代码时注释里出现「删除」会多问一次。我选择接受——多问一次的
成本是一次点击，漏问一次的成本是文件没了。

### 29.4% 这个数字本身偏悲观

用中文音色念 `docker`，得到的是「多克」。那是 TTS 的局限，不是用户的说法。
补一版双语拼接语料：中文段用中文音色、术语段用英文音色，拼起来。

| 语料 | 术语召回 |
| :--- | ---: |
| 中文音色念术语 | 29.4% |
| 双语拼接（更接近真人） | **47.1%** |

两版都远低于 95%，所以 GAP 的结论不变；但真实水平大概率落在两者之间。只报 29.4%
是把模型说得比实际差——这跟上一轮「拿英文句当混说成绩」是同一个毛病的反面：
**用一版语料冒充全部真相**。现在 `make verify` 一次报两个数。

### 文档数字：手工同步三遍，三遍都漏

这一轮测试数改了三次（158 → 161 → 173），每次都漏一处：README 写 161、路线图写
160、验收表写 157。而且验收表正文写着「见第 19 项」，表里根本没有第 19 项。

根因不是手滑，是**历史数字和当前数字用了同一种写法**。每加一轮，上一轮的
「验收项 17 → **18 项**」就变成一句谎话，而它看起来和当前值一模一样。

改法：每轮只记增量（「测试 +16」），绝对值只写在 Task 1.8 工程化那一节。
守卫是 `tests/test_docs.py` 的 5 条：

| 守卫 | 守什么 |
| :--- | :--- |
| 测试数一致 | 「N 项测试 / N passed」在三个文件里必须是同一个数 |
| 测试数真实 | 那个数必须等于 `pytest --collect-only` 数出来的 |
| 界面断言条数 | 必须等于 `len(audit_ui.CHECKS)` |
| 验收表编号 | 连续无断档，且和「N 项验收指标」对得上 |
| 代码度量表 | 每个文件的行数、合计，必须等于真实行数 |

写完它立刻抓到了我自己刚改的 `corpus.py`（文档 173 / 实际 224）——这说明它守的
正是最容易出错的地方。注入回归也做了：把 README 的 173 改成 172，它精确报出
`172 ← README.md:24`，并指出另外三处仍是 173。
